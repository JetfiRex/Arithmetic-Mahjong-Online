# 四人联机设计

范围：当前房间、身份、权限和同步合同，包含前端本地整理、正式动作实体提交和统一权威最右默认出牌。

## 运行架构

`multiplayer.web` 使用 FastAPI/Uvicorn 单实例、单 worker。房间、身份和分数保存在内存，重启清空；多个房间各有独立牌局。当前状态不能靠直接增加 worker 或实例共享。

浏览器共用 `UI/static/` 牌桌，通过 `multiplayer/static/client.js` 接入同源 HTTP 和 WebSocket。Bot 使用有预算的 CPU 子进程，不在网络事件循环中同步计算策略。

入口配置见 [README](../README.md)，部署见 [云端部署](cloud_deployment.md)，断线处理见 [运行层](hosting_design.md)。

## 房间和座位

- 房间最多十位真人、三位 Bot，Bot 不占真人名额；开局恰好四席。
- 创建/加入使用房间名、用户名和密码；房间名与房内用户名规范化后唯一。
- 房主安排四个不同且在线的席位，自己可以只观战；不要求额外全员准备。
- 开局锁定本局参赛映射、规则、计时和快速模式。快速模式默认关闭，独立于计时；开启后自动跳过无要牌资格的响应，并在全部相关决策完成后立即裁决，详见 [计时设计](action_timeout_design.md)。对局中可以移出观众，不能移除参赛者；房主离开会关闭房间。
- 成员身份和计分座位分开。下一局换人继承所在座位分数，换人不额外结算。
- 首局庄家为座位 0，之后每局固定轮换一次，不因胜负或模式改变。
- 每局发牌后先提供默认 30 秒的理牌时间，房主可设 0～600 秒；到期后庄家摸牌，t3 才开始。理牌时房间仍为 `PLAYING`，配置锁定，暂停与重连沿用同一套时钟处理。

```text
WAITING_PLAYERS → PLAYING → REVIEWING → ARRANGING → PLAYING
```

暂停使用独立运行标记，冻结计时和行动，不替代正常房间阶段。

结算后进入 `REVIEWING`；房主点击下一局进入 `ARRANGING`，可安排人员、模式和计时。两阶段均可查看上一结算局牌山；最终确认开局才轮庄、洗牌、发牌并关闭旧局查询。

## 身份和重连

站点邀请码控制进入权限，房间密码控制入房。服务器签发随机 Bearer 凭证，按凭证、有效连接和本局席位映射决定权限，不信任请求自报的玩家或席位。

标签页用 `sessionStorage` 保存凭证，已入房身份同时保存到同源 `localStorage`。新玩家窗口建立独立身份；同一身份的多个连接不增加成员或席位。

使用原房间名、用户名和密码加入时，原同名真人已离线则接回原成员并废弃旧凭证，仍在线则拒绝重名。Bot 不能被同名登录接管。恢复范围限于仍存在的内存房间，见 [运行与断线](hosting_design.md)。

## 玩家与观战视图

- 参赛者只看自己的暗牌及可操作提示。
- 公共观众看公开状态，上帝观众可看四家暗牌和允许的倒计时。
- 观众可选择把哪个座位放在下方，其余座位相对旋转；观察某席不获得控制权。
- 房主没有额外暗牌或牌山权限。
- 未提交排列、高亮、他人合法候选、未裁决响应和未来牌山不广播。

有暗牌权限的观众只在成功出牌后看到提交顺序；真实摸牌、消耗牌、副露、回合和结算仍正常同步。

## 同步与版本

| 接口 | 用途 |
| --- | --- |
| `POST /api/local/session` | 邀请校验、创建身份 |
| `GET /api/local/state` | 获取本人权限过滤状态 |
| `POST /api/local/action` | 正式动作、房间管理 |
| `WS /api/local/presence` | 认证连接存活、刷新交接和独立房间聊天 |
| `GET /api/local/wall-record` | 当前结算局的牌山查询 |

WebSocket 承载连接认证及房间聊天，不承载游戏命令或牌局状态推送。聊天独立于状态快照和版本，不触发牌桌重绘，详见 [房间聊天](chat_design.md)。

| 标识 | 作用 |
| --- | --- |
| `server_instance_id / room_id / round_id` | 隔离开服、房间和牌局 |
| `connection_id / control_epoch` | 有效连接和控制权 |
| `room_revision` | 成员、座位和设置版本 |
| `hand_revision` | 本人权威牌张版本，本地整理不改变 |
| 状态 `revision` | 同一查看者的状态顺序，拒绝旧回包 |
| 行动窗口 ID | 隔离 t1/t2/t3/t4 操作 |
| 本地布局版本 | 仅前端维护，不触发同步 |

房间操作和计时串行执行。同一 t1 多人响应不因先后更新全局状态而失效，本人整理也不改变他人的行动资格。

## 正式动作合同

- 命令带 `command_id` 及适用身份、局、窗口和手牌版本，服务器补全真实玩家身份。
- 重试沿用原 ID；同 ID 不同内容拒绝，成功命令不重复执行。
- 后端按自己的时钟处理到期窗口，再验证和执行动作。
- 出牌仅在顺序变化时附带出牌前完整 `hand_order`，顺序和动作原子提交，失败不能部分改顺序。
- 吃碰杠提交前端选定的实体，后端验证并绑定，不能按旧布局另选同值牌。
- 未确认行动显示为提交中，不永久修改权威牌局；合法的本地整理和状态接收继续。
- 权威回包只校正真实牌张增减，不覆盖新本地排列；迟到动作不能覆盖已执行超时结果。

细节见 [手牌整理](hand_order_design.md) 和 [Action 与 Timeout](action_timeout_design.md)。

## 超时与安全

所有 t3 超时和断线默认出牌取后端最新权威顺序最右实体，顺序已计入吃碰杠消耗、摸牌和补摸。前端按 ID 删除实际离手牌，保留其余本地排列，不回传整理结果。

后端校验 Host/Origin、JSON 大小、速率、角色和控制权；静态资源采用白名单，不开放编辑手牌、牌山、任意快照或调试接口。健康探测只暴露运行状态。

进行中牌山保密，结算后查询校验当前身份、房间、结算局和阶段。完整检查点及牌山记录见 [状态快照](state_recovery_design.md)。
